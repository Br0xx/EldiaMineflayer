# Minecraft Java 26.3 (protocol 777) for the 9bflayer fork

Added the same way as 26.2 (see [v26_2.md](v26_2.md)): data in `lib/mcdata/26.3/`, registered at load time by
`lib/mcdata/overlay.js` (which replaced `overlay26_2.js`; that name still exports the same thing).

## Where the data comes from

- minecraft-data's branch `pc_26_3` (bot commit e4cbec4, 2026-09-15) is **only a placeholder**: its `pc/26.3/protocol.json`
  is byte-identical to 26.1's and every other file is a pointer to `pc/26.1`. Nothing in it is 26.3.
- The real 26.3 data is minecraft-data PR #1301 (same head as #1304), commit 924e26d, by DallasCarraher, built on the 26.2
  PR. Its commit messages say the protocol was decompiled from the 26.3 server jar and checked against a Paper 26.3 server
  and a 26.3 Realm. Fetched with `git fetch origin refs/pull/1304/head`. Unmerged; the same trust level as the 26.2 PR.
- Shipped from it (minified): `protocol, blocks, blockCollisionShapes, items, entities, foods, recipes, version`.
  Everything else is inherited from 26.2: attributes, biomes, loginPacket, particles, sounds, language, tints, windows
  (as the PR's `dataPaths` does).
- `materials.json` is **derived**, not copied: the PR points 26.3 at 26.2's, but its tool ids are item ids and 26.3
  inserted 121 items, so every id would be off (a stone block took 46 ticks with a diamond pickaxe). It is 26.2's file with
  each tool id remapped by item name.
- minecraft-data's 26.3 `blocks.json` uses the material `incorrect_for_wooden_tool` for 108 blocks where our 26.2 copy (older
  commit 68ea7b5) has `mineable/pickaxe`. The PR's 26.2 changed the same way, so the shipped 26.2 is slightly behind it
  (block materials, `trial_spawner_detection` particle names, and the entity_action/hand names reverted to master's:
  `stop_sleeping`, `main_hand` mapper). Not updated here; `lib/entity_action.js` resolves both name sets.

## 26.2 to 26.3

Counts: blocks 1196 to 1286 (max state id 32365 to 35722, so the global palette is **16 bits**, was 15), items 1537 to 1658,
entities 158 to 161 (`cushion`, `poplar_boat`, `poplar_chest_boat`; `player` 156 to 159), data components 111 to 122.

Protocol (play unless noted):

| Change | Effect on the fork |
|---|---|
| light masks in `map_chunk` and `update_light` are `ByteArray` (a BitSet as bytes) instead of long arrays | `blocks.js` converts them back to the long pairs prismarine-chunk reads (`maskLongs`) |
| `rel_entity_move`, `entity_move_look`: `move: entityDelta` = `{ onGround, steps: [{ dX, dY, dZ, ticks }] }`, a new **native type**; `entity_move_look` lost `onGround` | minecraft-protocol 1.68 has no `entityDelta` (upstream PR nmp#1538): `lib/mcdata/entityDelta.js` adds it to the serializer tables. `entities.js` sums the steps |
| `sync_entity_position`: `positionType` linear (x, y, z) or stepped (steps), no `dx/dy/dz` | `entities.js` takes the last step and keeps the velocity when none is sent |
| serverbound `teleport_confirm` gains `x, y, z, yRot, xRot` | `physics.js` (`answerTeleport`) writes the position and rotation the bot applied (detected from the packet's fields) and sends **no `position_look` behind it**: Grim >= 26.3 (`CheckManagerListener`, `TELEPORT_CONTAINS_POSITION`) takes the confirm as the teleport and would read a following PosRot as an ordinary move from a standstill with `onGround` false. That the 26.3 client sends nothing after the confirm is inferred from Grim, not seen. Whether a real server accepts exactly these values is unverified |
| serverbound `block_dig` (player action) enum: `CHANGE_DESTROY_DIRECTION` inserted at 1 | abort 2, finish 3, drop stack 4, drop item 5, release 6, swap 7. `lib/player_action.js`; used by digging, inventory (release) and vanilla_interact (swap) |
| serverbound `punch` (void, 0x2e) new; `spectator_action` removed, `spectate` back; `arm_animation` is still there | what `punch` is for is unknown (commit text: "replaces the old arm_animation/swing packet"). The fork still swings with `arm_animation`. **Judge on a real server, and against Grim's 26.3 handling** |
| clientbound `swing_animation`, `post_effects`, `add_transient_block` new (ids shift) | parsed, unused |
| `world_particles` re-laid out (particle first, `xMaxSpeed...`, varint amount, `randomizationType`) | `particle.js` reads the new layout: `movementSpeed` is the largest of the three speeds when there is no `velocityOffset`, and `particle.maxSpeed` (Vec3) and `particle.randomizationType` carry the rest; fishing only needs `particle.type`, `amount`, x/z |
| `SlotComponentType` renumbered again, new components, `pot_decorations` is four `ItemStackTemplate`s | by the data; nothing hardcodes component ids |
| entity metadata: `optional_uuid` is `optional_living_entity_reference`, new `dye_color` | by the data |
| `teams` layout is back to the 26.1 order (26.2's was reordered) | `team.js` reads by field name |
| configuration `post_effects`, `ItemBlockProperty` min/max optional, `SlotDisplay.tag` is an `IDSet` | by the data |
| feature `playerActionHasChangeDestroyDirection` (26.3+) in minecraft-data | not added to minecraft-data's table here; `player_action.js` compares versions instead |
| `login` and `success` | unchanged from 26.2 (`onlineMode`, `sessionId`); the test harness fills `sessionId` for the mock server as before |

minecraft-protocol 1.68 needed no other change for the client. The mock server needs the `sessionId` shim (26.2 on) that
`test/internalTest.js` already has.

## Chunks (26.2 and 26.3)

prismarine-chunk 1.41 has no entry for either; the overlay lends them `pc/1.18/chunk` (upstream's PR #331 and #333 do the
same). Its reader sizes the global palette from the highest state id (`neededBits(maxStateId)`: 15 bits on 26.2, 16 on
26.3) and drops the data-array length prefix from 1.21.5. Tests build 1.18+ sections by hand from the wire format and
send them through the mock server: palettes of 4 bits, single value, a global-palette section of 4096 different states
including the highest state id (a block past the 26.1 count), read back with `blockAt` and `findBlocks`.
prismarine-chunk's light reader reads the 2048-byte nibble arrays as longs, which mixes the order inside each 8 bytes
(upstream PR #340). Block light and sky light values near a set value can be wrong; nothing in the fork uses them.

## What this does and does not prove

Proven with the mock server and serializer round trips: the data loads, the protocol compiles, packets round-trip, the
bot logs in, spawns, receives chunks of every shape above, entities move, windows open, and the library functions read what
a server like the PR's data describes.

Not proven, and only a real 26.3 server (Paper 26.3 on a local port is enough) can settle it:

- that the PR's wire data is right (it is one contributor's reading of the server jar);
- `teleport_confirm` (see above), the serverbound `punch` (open item: it has no fields, the PR calls it the replacement of
  `arm_animation`, and nobody has seen when the client sends it; the fork keeps writing `arm_animation`), and whether the
  new block-dig ids are what Grim 26.3 expects;
- the registry data inherited from 26.2: biome count (66), attribute order (40, the wire ids of `update_attributes` follow it),
  `particles.json` and `sounds.json` ids (26.3 inserted particles, so the particle names the fork emits are off);
- the `entityDelta` byte layout (taken from the nmp PR, which says it was checked on a local 26.3 server).
