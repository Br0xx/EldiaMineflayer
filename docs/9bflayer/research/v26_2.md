**entity_action** (verified by serializing):

- In 3.117.0, `entityActionUsesStringMapper` is **absent** from `features.json`, but the fork's `lib/plugins/physics.js` branches on it. Without it the fork sends numeric ids (`3`/`4` for sprint). On 1.21.6 through 26.1 the mapper name is `start_fall_flying`, so an unknown string serializes as 0 (`stop_sleeping`). That elytra bug already exists upstream for those versions. It is not a 26.2 problem.

## 2. Getting `require('minecraft-data')('26.2')` to work (overlay, proven)

### How minecraft-data 3.117.0 resolves a version

`index.js` does `toMajor('26.2')`, which finds the row in `protocolVersions.json` (present) and then reads `data.pc['26.2']` from `data.js`. That key does not exist, so it returns `null`. `data.js` is a plain mutable object (`module.exports = {pc: {..., '26.1': {get blocks(){...}, ...}}}`), and `index.js` holds the same object. `package.json` has no `exports` map, so `require('minecraft-data/data.js')` is allowed. `supportFeature` uses the `dataVersion` of the `protocolVersions.json` rows, which is why the 26.2 row's `dataVersion` of 4903 matters.

### Feature ranges

Checked every entry in `features.json`: **no range ends at `26.1`**. All the open ones say `latest`, so 26.2 inherits every feature (verified: the 10 features I compared, among them `newPlayerInputPacket`, `sendsClientTickEndPacket`, `attackUsesOwnPacket`, `useEntityHasLocation`, `sendsPlayerLoadedPacket` and `positionPacketHasBitflags`, are identical on 26.1 and 26.2). The only addition needed is `entityActionUsesStringMapper` (`["1.21.6","latest"]`, copied from the branch's `features.json`). Do not use the branch's whole `features.json`/`protocolVersions.json`: they are older than 3.117.0 (the branch lacks 26.3 and has no newer fixes).

### Packaging

- Location: `lib/mcdata/` (not `lib/data/`: the fork's `.gitignore` ends with a bare `data` line, so `git check-ignore` confirms `lib/data/26.2/blocks.json` would be ignored).
- Shipped files (`lib/mcdata/26.2/`): attributes, biomes, blockCollisionShapes, blocks, entities, foods, items, language, loginPacket, materials, particles, protocol, recipes, sounds, tints, version, windows. That is 17 files.
- Everything else (effects, enchantments, instruments, mapIcons, blockLoot, entityLoot, commands) is inherited from the module's own 26.1 entry through `Object.getOwnPropertyDescriptors`, so the lazy getters stay lazy.
- Why those three are skipped: the 26.2 branch ships newer `blockLoot` (213 KB), `entityLoot` (19 KB) and `commands` (848 KB), but mineflayer reads none of them (grep of `lib`). If wanted later they can be added to `LOCAL` in the overlay.
- The branch's `dataPaths.json` entry for 26.2 is not usable as-is: it also changes the 26.1 entry (`proto` points to `pc/26.1`) and lists `windows: pc/1.20.3`. Copying only the data files avoids this.
- Sizes: raw pretty-printed JSON is about 5.14 MB. **Minified** it is 2,427,630 bytes. A gzipped tar is about 350 KB. Biggest: blockCollisionShapes 579 KB, blocks 551 KB, language 487 KB, loginPacket 238 KB, items 141 KB, recipes 131 KB, protocol 119 KB. Minify when copying:

### The overlay (`lib/mcdata/overlay26_2.js`, passes `standard`)

`install(roots = defaultRoots())` runs, for every distinct `minecraft-data` copy reachable from the fork and from nmp/prismarine-*:

1. `patchFeatures`: adds `entityActionUsesStringMapper` if missing (must run before the first `minecraftData('<version>')` call because `supportFeature` maps are cached per version).
2. `patchOne`: returns `'upstream'` and does nothing when `data.pc['26.2']` already exists. Otherwise it adds the 26.2 row to the version tables only if it is missing (older minecraft-data builds; tested by deleting the row), pushes `'26.2'` into `supportedVersions.pc`, builds `data.pc['26.2']` from 26.1's descriptors plus lazy getters for the shipped files.
3. `patchChunk`: replaces the cached export of `prismarine-chunk` with a wrapper that asks the original first (muting its `console.error`) and, only for `pc` + majorVersion `26.2` when the original throws, builds `prismarine-chunk/src/pc/1.18/chunk`. The 1.18 implementation already branches on `>= 26.1` for the fluid-count field. When upstream adds the key, the original succeeds and the wrapper is a pass-through.
4. `patchPhysicsFeatures`: appends `'26.2'` to every entry of the npm `prismarine-physics` features that contains `'26.1'` (idempotent).

Install it as the **first line of `lib/loader.js`** (before nmp or the prismarine libs are required; the patch does that).

## 3. Does nmp 1.68.0 need code changes? (checked against `pc26_2`)

- **Client login: no code change.** The loopback logs in against 26.2 with the installed, unmodified nmp 1.68.0 client. The only references to `version.js` are `defaultVersion` (used when no `version` is given) and the exported `supportedVersions` (informational). `createClient` only requires `require('minecraft-data')(version)` to return data, which the overlay provides. `serializer.js` also checks that the data's protocol number equals the row in `versionsByMinecraftVersion`: 776 matches.
- Optional, `nmp-26_2.patch` (3 hunks, `patch -p1`):
  1. `src/version.js`: add `'26.2'` to `supportedVersions` (cosmetic). I left `defaultVersion` at `26.1` to avoid changing behaviour. At runtime without patching nmp, `require('minecraft-protocol').supportedVersions.push('26.2')` gives the same effect.
  2. `src/server/login.js`: `success` now includes `sessionId: crypto.randomUUID()`. Only nmp's **server** needs it (tests, local rigs). Without it, `createServer({version:'26.2'})` fails on the first login with `Write error ... UUID ... reading 'length'` (reproduced with the unpatched copy; the patched copy works with no shim).
  3. `docs/README.md`: version list.
- Because the fork consumes nmp as an npm dependency, there is nothing to commit for the client. Keep `minecraft-protocol` on `^1.67`/`1.68` and leave the version list alone, or vendor the patch via `patch-package` if the server hunk is wanted.

## 4. Recommended packaging, step by step

1. Copy `/home/user/ref/v262-scratch/lib/mcdata/` to `<fork>/lib/mcdata/` (check `git status`: it must not be ignored; it isn't).
2. `cd <fork> && patch -p1 < /home/user/ref/notes/fork-26_2.patch` (dry run on the live fork returned 0).
3. `npx standard` (passes on the new files), then `git add lib/mcdata && git commit`.
4. Optional extras (not part of the patch, need decisions from whoever owns those files): `bed.js wake()` should write `'leave_bed'` on 26.2 (and `'stop_sleeping'` on 1.21.6 to 26.1); `lib/team.js` `colorString()` should treat `null` like `undefined`.
5. Smoke test: `node /home/user/ref/v262-scratch/loopback_final.js` (its server side uses the patched nmp copy `nmp-patched/`; `loopback.js` is the variant with a `beforeLogin` shim for the unpatched nmp). Then try a real 26.2 server, see section 6.

**No-op when upstream ships 26.2.** Once `minecraft-data` includes `pc/26.2` (any release with `data.pc['26.2']`), `patchOne` returns `'upstream'`, the feature is `'present'` as soon as the data includes it, the chunk wrapper falls through to the real implementation as soon as prismarine-chunk adds the key, and the physics edit is idempotent. Cleanup then: delete `lib/mcdata/`, remove the first line of `lib/loader.js`, keep the version/feature-table edits (or drop them when the published prismarine-physics covers 26.2; the fork's own `lib/physics/features.json` is a vendored copy and keeps the edit). `npm view minecraft-data` today shows no release after 3.117.0 (2026-09-22).

## 6. Risks and things only a real server can confirm

1. **Wire data of PR #1298 is unmerged and unverified here.** Highest risk: `teams` field reorder, `login` `onlineMode`, `success` `sessionId`, the `Particle` `geyser*` extra fields and the `SlotComponent` shift. On a wrong decode the bot would be disconnected by a parse error. Mitigation: first connect to a 26.2 server with `hideErrors: false` and a `packet` listener, then confirm the join and the first chunk batch.
2. **Attribute ids.** The `update_attributes` key mapper in the protocol data has 31 entries (identical in 26.1 and 26.2) but `attributes.json` has 35 (26.1) and 40 (26.2) in registry order. Even in 1.21.1 through 26.1, the mapper is stale after a few ids (`movement_speed` is id 17 in the 1.21.1 and 1.21.4 mapper but index 21 in `attributes.json`; 20 vs 22 in 1.21.8 through 26.1). On 26.2 five more attributes are inserted at the front, so ids from 0 on change. Anything keyed on the attribute name that comes off the wire (movement speed in `lib/physics/engine.js`, which looks up `mcData.attributesByName.movementSpeed.resource`) needs to be checked against a real 26.2 server, and the key names (`generic.*` in the mapper vs `minecraft:*` resources) already differ. If it is wrong, the correct fix is to generate the mapper from `attributes.json` order. This predates 26.2 and is not fixed here.
3. **Chunk format.** The 1.18 chunk implementation (with the 26.1 fluid-count field) is assumed unchanged. The protocol data has no change in `map_chunk`; I could not check the section encoding itself.
4. **Movement physics.** 26.2 adds the `friction_modifier`, `air_drag_modifier` and `bounciness` attributes. The fork's physics (vendored from prismarine-physics) knows nothing about them, which is harmless for default values (1, 1, 0). The Grim-compat behaviour on 26.2 must be judged on the real server.
5. **Version-keyed caches:** `supportFeature` and `minecraftData(version)` results are cached per version, so the overlay must run before anything creates data for versions it changes (`entityActionUsesStringMapper` also changes 1.21.6 to 26.1). It is the first line of `loader.js`, which is why.
6. The entity-action fix (`entityActionUsesStringMapper` for 1.21.6+) changes behaviour on 1.21.6 to 26.1: sprint now uses strings, which is correct; before, it sent horse-jump ids. The 1.21.4 path (9b9t) is unaffected (range starts at 1.21.6).
